01评审结论

定位：受控 ReAct 问答工作台 + 文档治理后台，不是通用聊天壳。Pivot 的工具白名单只有检索与读证据两类，答案必须过门禁，所以界面的第一优先级是「过程可见、证据可查、状态可对账」，对话区只是其中一栏；租约、检查点、预算对账这些执行状态必须常驻可见，而不是藏进设置里。

只参考样稿的功能设计，不借鉴它的前端设计。样稿 v17 里值得借的是功能分区与流程约束——主页 / 问答 / 文档库 / 审批队列 / 移动请求 / 审计六个功能域、审批的先后顺序、移动的单边审批、认领拦截、审计事件口径、异步导出——这些是功能层面的划分，本样本照此对齐。本样本五页是六域的子集映射：问答台＝问答区，知识库＝文档库区，运营看板＝主页总览与审计的简化合并，成员与权限、系统设置对应角色与配置面。审批队列与移动请求在功能设计里是独立域，正式版必须独立成页，不能塞进知识库页凑数。

视觉设计为本样本自有方案。样稿的灰白底、石板灰主色、小圆角与密集小字排版一概不用；本样本用自己的令牌体系：暖陶土的米白画布配陶土橙与衬线标题、深夜专业的深色面板配柔和橙，圆角、间距、顶栏加页面导航的布局都是按这套令牌自排的。组件只消费 CSS 变量、不写死颜色，切换即换 data-theme。主题只保留这两套，顶栏只放一个太阳 / 月亮图标按钮一键切换。企业极简已下线，避免三套主题稀释维护成本。

部门按可变集合设计，不按固定名单设计（FR-RBAC-004）。部门在后端就是一种库：Library 只有 id / name / kind / dept_id 四个字段，成员归属 Membership 是六字段关系，部门内角色只有部门管理员（dept_admin）/ 编者（editor）/ 读者（reader）三档，全局管理员是独立的系统角色、不在这三档里。部门数量后期一定会变，所以任何部门选项都不许写死：知识库的部门筛选、加成员的部门下拉、成员列表的部门过滤，全部从部门数据动态拉取；后端列表接口无分页、一次返回全量，部门多了以后前端用「先搜索、再滚动选择」承载，不做写死的前几个加一个「更多」。部门管理员的可见范围只有公共库加本人管理的部门库，其他部门在他的界面里按不存在处理。

红队保留意见：样本里最容易被误读的三处——运营看板的数字是合成示例，不能当真实运营指标；设置页的检索阈值类数值是 DR-010 候选值，未冻结前不得当生产参数；审批顺序与移动的单边审批是后端状态机约束，前端只能如实呈现，不许为了「顺手」简化掉。

04落地约束（红队审查后保留）

  • 状态机不可简化：审批批准按「关请求 → 改写库 → 触发 ingest」在泳道里原样呈现；移动审批只给目标库管理员决策入口，源库管理员视图不渲染决策按钮。
  • 权限即界面：不可见的库按「不存在」处理——不渲染、不计数、不在搜索与选择器里暗示其存在，与功能设计中上传选到不可见库被拒绝的口径一致。部门同理：部门管理员只看公共库与本人管理的部门，其他部门不进他的部门列表与选择器。
  • 部门不写死：部门集合、部门计数、部门下拉与筛选一律由数据计算，禁止在界面代码里枚举部门名或部门个数；后端列表无分页返回全量，前端必须用搜索加滚动列表承载，部门涨到几十个也不改版式。新建部门后所有选择器立即出现该部门，不用刷新配置。
  • 部门生命周期如实呈现：后端只有创建与删除接口，前端不许自创改名、停用、合并入口。改名走「迁空 → 删除 → 重建」；合并走移动审批逐批移文档、逐一迁成员、最后删空部门；删除前必须校验并向操作人明示残留成员数与文档数，有残留直接拦住并给出迁移路径，不许先删后补。已删除的部门必须从知识库筛选、加成员下拉、成员过滤等全部选择器中同步消失，不留幽灵选项。
  • 数值纪律：DR-010 未冻结前，阈值类数值在界面上标注候选 / 样本；GATE-P0 未验证前，任何页面不得出现「已上线」「已验收」表述，只能写开发实现与样本演示。
  • 双主题纪律：新部件只准使用本样本自有主题变量（画布 / 面板 / 发丝线 / 文字三档 / 强调色），禁止写死颜色值，否则一键切换会出现漏网区块；主题切换只保留顶栏一个太阳 / 月亮图标按钮，不再另设分段控件；本次评审已按此标准核对现有五页。

05部门场景走查（真实业务里会发生的变化）

  • 新增部门：全局管理员建部门 → 部门列表、知识库筛选项、加成员下拉三处同步出现；先指派一名部门管理员，再逐个加编者与读者，空部门在列表里如实显示 0 人 0 文档。
  • 部门改名：没有改名接口，不提供改名输入框。真要改名：把文档经移动审批迁到新部门、逐一迁成员归属、删掉空的旧部门再按新名重建，过程全程留审计，前端只呈现这条路径、不假装能一键改名。
  • 部门合并：没有合并接口。走跨库移动的单边审批逐批移文档（只由目标部门管理员决定），成员逐一改归属到目标部门并重定三档角色，确认源部门 0 人 0 文档后才允许删除。
  • 部门停用 / 删除：没有停用态。删除前校验并提示「还剩 N 名成员、M 份文档」，有残留删不了；删空后二次确认才执行，删完该部门从所有选择器中消失，历史审计仍保留原部门名、不回写。
  • 部门变多：样本已内置十余个部门演示量级；正式版部门涨到几十个时，列表接口仍是全量返回，前端靠搜索过滤加滚动列表与按部门过滤成员，版式与部件都不需要改。
  • 部门管理员越界：切到部门管理员视角后，部门列表只剩本人部门、成员列表只剩本人部门成员、加成员的部门下拉锁定本人部门；其他部门连数量都不显示，避免从计数反推组织信息。
