# Pivot 前端工程设计评审

## 评审说明

本次评审只做设计结论，不改任何代码和样本。评审对象是 Pivot 仓库 `web/` 与 `api/` 的实际功能，评审基准是 main 头 `bce228e`（2026 年 11 月 4 日提交），评审日期是 2026 年 11 月 6 日。

证据边界有两条。第一，GATE-P0 全部未验证，DR-010 生产数值尚未冻结，开发实现不等于运行批准。前端设计结论只针对开发实现阶段，不承诺验收结果。第二，凡是仓库里没有的功能，本评审一律按不存在处理，不编造页面和接口。

口径说明：风格样稿目录下的 `问枢前端参考v17.html` 与 S1 至 S6 样稿，本评审只参考它们的功能设计，也就是有哪些页面、哪些功能、什么流程、部件承担什么功能。样稿的视觉风格、配色、令牌、布局结构、六区架构这类设计层面的东西一律不采用，也不写入结论。视觉与主题方案只保留已定的两套，也就是暖陶土与深夜专业，两套都来自 open-claude-ui 的 CDS 令牌，与样稿无关。

本文按仓库内 `docs/document-style-guide/` 中的 ruanyf《中文技术文档写作规范》现行版本写作。

2026 年 11 月 6 日修订：按真实业务场景重写部门设计。部门数量后期会变，第 6.10 节按新增、合并、改名、停用四种场景重写，第 1.1 节、第 1.2 节、第 2.1 节、第 6.8 节、第 7 节、第 8 节与第 10 节同步修订。

## 1 评审结论

### 1.1 设计决策总览

| 决策项 | 结论 |
|---|---|
| 技术栈 | 保持 Next.js 14.2.15 加 React 18.3.1，不引入第三方 UI 库，不新增依赖 |
| 路由 | 保持现有 10 页路由结构不变，不按样稿的六区架构重组 |
| 布局 | 保持 Topbar 加 Shell 的现有布局，对话页保持侧栏加主区加证据抽屉的三段式工作区 |
| 主题 | 只保留暖陶土与深夜专业两套，一键切换，令牌来自 open-claude-ui 的 CDS |
| 数据流 | 保持现有模式：REST 加 SSE 流式问答，访问令牌只放内存，刷新令牌走 HttpOnly Cookie |
| 状态管理 | 保持页面内 `useState` 加 `lib` 层函数，不引入全局状态库 |
| 第二阶段 | 审批、移动、部门库三组功能后端接口已备，前端尚未接线，列为第二阶段；其中部门库页是三组中最复杂的一组，部件清单见第 6.10 节 |
| 部门数据 | 一律动态拉取，不得写死；部门数量从几个变到几十个时靠搜索与前端过滤承载，不设固定上限；部门没有改名接口与停用状态 |
| 样本纠偏 | 之前样本示例里的运营看板、成员与权限、系统设置三页不是真实功能，不得当作路线图 |

### 1.2 关键判断

第一，前端底子已经够用。10 页路由、登录、问答、搜索、知识库、后台四页都已实现，缺的是主题切换和三组后端已备功能的接线，不是重写。

第二，样稿的价值在功能清单，不在视觉。样稿覆盖的审批队列、移动请求、认领流程、审计筛选、导出流程，与后端 `approvals.py`、`moves.py`、`departments.py` 的接口一一对应，可以直接当作第二阶段的需求输入。样稿的配色、令牌、布局一律不采用。

第三，主题切换是本轮唯一的全局改动。改动集中在 `app/globals.css` 的令牌层和一个主题切换部件，其余页面只换令牌，不动结构。`tests/e2e/fixtures/web/test-foundation.mjs` 对现有令牌值有断言，改令牌必须同步改这份测试。

第四，open-claude-ui 只复用令牌组织方式和交互模式，不复制它的界面。open-claude-ui 是 Claude 桌面端的高保真复刻，原样照搬有商标与商业外观风险。Pivot 对外产品的界面必须用自己的品牌表达，只借它的令牌分层、输入框、思考折叠、模型切换这类通用模式。

第五，部门是动态数据，不是固定配置。部门数量后期会变，部门的新增、合并、改名、停用都要按真实业务场景走后端已有的能力：新增走创建接口，合并走移动审批加删除，改名没有接口只能删了重建，停用没有状态只能清空后删除。前端所有涉及部门的地方一律动态拉取，不得写死部门列表。

## 2 评审依据

### 2.1 仓库实际功能盘点

用户侧路由共 7 页：登录页 `/login`、首页 `/`、知识库 `/library`、文档详情 `/library/[id]`、全局搜索 `/search`、对话 `/chat`、会话详情 `/chat/[id]`。管理侧路由共 4 页：后台概览 `/admin`、文档管理 `/admin/docs`、用户管理 `/admin/users`、审计日志 `/admin/audit`。另有一个 SSE 代理路由 `/api/v1/runs/[id]/events`，用于去缓冲转发。

用户侧后端能力有：登录、刷新、退出；会话列表、详情、创建；消息列表；创建问答运行（带幂等键）；SSE 事件流；取消运行；澄清续答；文档列表与详情；文档搜索；会话导出（Markdown 与 Word）。

管理侧后端能力有：运行指标、解析任务列表；文档上传、重试、删除；用户列表、创建、启用与停用；审计事件查询。角色只有管理员与普通用户两档，403 统一走无权限页。

服务端已有、前端尚未接线的能力有三组。审批组：待审批列表、详情、批准、拒绝、撤回、重提、改目标、评审记录。移动组：待决移动列表、详情、创建、批准、拒绝、撤回。部门库组：部门库创建、列表、详情、删除、成员管理、文件夹、例外授权、未分配文档认领。这些接口在 `api/src/pivot/http/departments.py` 中已经实现，前端 `web/` 没有对应页面和调用，也没有任何与部门相关的代码。约束有五条。第一，列表接口无分页，返回全量，`pagination` 为 `null`，部门数量增长时前端靠搜索与前端过滤承载。第二，部门只有创建与删除两个生命周期接口，没有改名接口，也没有停用状态，合并只能走移动审批加删除。第三，部门编号创建后不可改，须符合 `[a-z0-9][a-z0-9_-]{0,127}`，名称 1 至 255 字。第四，删除部门要求无成员且无活文档，否则后端拒绝。第五，部门管理员只看到公共库与本人管理的部门，跨部门访问后端返回 404，普通用户请求部门列表返回 403。

### 2.2 样稿的功能参考范围

样稿可参考的功能设计如下。主页：提问直达问答、待办计数分流、库总览、最近动态、快捷入口。问答区：会话历史分组与搜索、新建会话、输入框、附件入口、可见库提示、Agent 状态面板（步骤、预算、上下文用量）。文档库区：上传时选目标库、文件夹树、文档表、认领流程（未分配文档认领进目标库，带未决请求时拒绝认领）。审批区：队列、任务详情、申请理由、审计轨迹、全过程泳道。移动区：移动请求表、批准、拒绝、撤回、文件夹归并说明。审计区：按操作人、事件、库三档筛选。导出：导出格式选择与状态提示。

样稿不参考的部分如下。全部配色与令牌值、六区导航结构、侧栏宽度与字号档位、按钮与卡片的视觉样式、动效细节。这些内容与 Pivot 现有前端无关，不进入结论。

样稿本身是静态原型，数据按真实功能口径编造，按钮不接通后端。引用样稿的功能点时，必须以 `api/` 的实际接口为准核对，接口没有的字段不得当作需求。

### 2.3 open-claude-ui 复用范围

可复用的有三类。第一是令牌组织方式：表面分层、边框分层、文字分层、强调色链、圆角档位、阴影档位、焦点环，见第 5 节。第二是交互模式：输入框自动增高、思考过程折叠、流式输出与停止、引用编号点开证据、会话列表分组、模型切换带用量条、操作确认弹窗。第三是工程习惯：原子写入配置、键盘快捷键、焦点管理。

不复用的有两类。第一是 Claude 桌面端的整体布局与视觉特征，包括三栏比例、米白加陶土橙之外的品牌表达、动效物理参数原值。第二是把它当作依赖引入。open-claude-ui 不进入 `package.json`，只手工借鉴令牌与模式，代码由 Pivot 自己写。

## 3 技术栈与工程取舍

前端保持 Next.js 14.2.15 加 React 18.3.1，`web/package.json` 的运行时依赖只有这两项加 `react-dom`，零第三方 UI 库。本评审决定不引入组件库，理由有三条。第一，现有基础组件已经齐备，见第 6 节。第二，引入组件库会带来主题令牌的第二套来源，与一键切换两套主题的目标冲突。第三，Pivot 是企业内用系统，组件数量有限，自写成本低于适配成本。

不引入的状态库与动效库，理由相同。页面状态已经由 `ChatViewState` 这类局部状态机表达清楚，全局只有一个访问令牌，且只放内存变量。动效只用 CSS 过渡，满足输入框、抽屉、弹窗的需要。open-claude-ui 的动效引擎只作参考，不移植。

保留的工程约定有四条。第一，类型检查与 Lint 保持现状，`npm run typecheck` 与 `npm run lint` 通过才合入。第二，错误统一走 `ApiError` 信封，含错误码、信息、请求 ID、是否可重试。第三，测试基线保持现状：`test-foundation.mjs` 的令牌断言随主题改动同步更新，Playwright 十页默认跳过。第四，样式集中在三份 CSS 文件：`app/globals.css` 放全局令牌与基础组件样式，`app/(user)/user.css` 放用户侧页面样式，`app/(admin)/admin.css` 放管理侧页面样式，主题变量只在 `globals.css` 定义。

## 4 路由与布局

### 4.1 路由结构

路由保持 App Router 的两个路由组。用户组在 `app/(user)/`，管理组在 `app/(admin)/`。第二阶段新增的审批、移动、部门库页面挂在管理组下，路径另行定，不动现有 10 页的路径。首页、知识库、对话三项主导航保持不变，全局搜索保持 Ctrl+K 聚焦。

### 4.2 布局结构

布局保持两层壳。用户侧是 `UserShell`，含 `SessionGate` 会话守卫与 `Topbar` 顶栏，顶栏含品牌、主导航、全局搜索、退出登录。管理侧是 `AdminAppShell`，同样含会话守卫与顶栏，下方是 `AdminShell` 的侧栏加内容区，侧栏四项是概览、文档管理、用户管理、审计日志。

对话页的工作区保持现有三段式：左侧会话列表、中部消息流与输入框、右侧证据抽屉。这是现有 `ChatWorkspace` 已实现的结构，也是问答功能的实际需要，与样稿无关。移动端窄屏时，侧栏与证据抽屉改为抽屉打开，不常驻。

页面状态统一用四档：加载中、就绪、空、错误，管理侧再加无权限一档。所有列表页空态都要有文字说明，不留空白页。

## 5 主题方案

### 5.1 两套主题与切换机制

只保留暖陶土与深夜专业两套主题，之前样本示例里的企业极简一并去掉。切换方式是一键切换，切换控件放在顶栏右端，全站生效，刷新后保持上次选择。首次访问默认跟随系统深色模式，系统为深色时默认深夜专业，否则默认暖陶土。

实现方式是 `html` 元素上的 `data-theme` 属性，取值为 `warm` 或 `dark`。切换时只改属性值，不改 DOM 结构。选择存在 `localStorage`，键名另行定。为避免首屏闪烁，主题初始化脚本放在 `app/layout.tsx` 的 `head` 内联执行，在渲染前读存储值并写属性。服务端渲染不依赖主题，不做按主题分流。

### 5.2 令牌组织

令牌全部来自 open-claude-ui 的 CDS，与样稿无关。组织方式分六组：表面、边框、文字、强调色、圆角、阴影。每组只定义语义变量，组件样式只引用语义变量，不写色值。现有 CSS 文件引用的 `--c-*` 变量名保持不变，只改变量值，避免 991 行样式大面积改动。新增变量只补缺口，主要是陶土强调色链。

暖陶土的令牌值如下。表面：底层 `#f9f9f7`、主画布 `#fcfcfb`、卡片与输入框 `#ffffff`。文字：主文字 `#0b0b0b`、次文字 `#52514e`、弱文字 `#898781`。强调色：陶土 `#d97757`、加深陶土 `#c6613f`、极浅陶土底 `#fbf3ef`；链接与焦点 accent 蓝 `#184f95`。圆角：基础 8px，输入框 12px。阴影：小、中、大三档，透明度递增。

深夜专业的令牌值如下。表面与文字整体倒转，主文字 `#f0efec`，次文字与弱文字沿用 CDS 暗色档。陶土强调色双模同值，`#d97757` 与 `#c6613f` 不变，暗色下悬停加深态为 `#e08264`。链接与焦点 accent 蓝改为 `#6da7ec`，边框强调色为 `#0d366b`。圆角与阴影档位与暖陶土相同，阴影透明度按暗色调整。

约束有一条。`tests/e2e/fixtures/web/test-foundation.mjs` 对现有令牌值有精确断言，改令牌必须同步更新这份测试，改为断言两套主题各自的变量值。不断言通过的令牌改动不得合入。

### 5.3 与样稿的边界

S5 暖米阅读与 S6 深色霓虹的配色不采用。S5 的暖米色系与暖陶土方向接近，但色值与令牌结构不同，不混用。S6 的霓虹渐变与深夜专业的克制暗色方向相反，明确排除。S1 至 S4 的配色同样不采用。主题评审只认 CDS 这一处来源。

## 6 按页部件清单

清单的写法统一为四列：部件、对应后端能力、状态与交互要点、复用来源。复用来源只写四类：现有、CDS、v17 功能参考、新写。凡是后端没有接口的部件，一律不列入本节，见第 8 节。

#### 6.10.1 部门库页：部件清单

部门就是库。`Library` 模型只有四个字段：编号 `id`（主键，128 字以内）、名称 `name`（255 字以内）、种类 `kind`、归属部门 `dept_id`。部门库的 `kind` 为 `department`，`dept_id` 与自身编号相同；项目库的 `kind` 为 `project`，`dept_id` 是归属部门的编号。成员模型 `Membership` 只有六个字段：用户编号、部门编号、部门内角色、授权人、授权时间、过期时间。部门内角色只有三档：部门管理员、编者、读者。过期时间为空表示长期授权，到期后读不到，续期须显式延长。

| 部件 | 对应后端能力 | 状态与交互要点 | 复用来源 |
|---|---|---|---|
| 部门列表 | `GET /admin/departments` | 动态拉取全部返回结果，接口无分页（`pagination` 为 `null`），前端做搜索过滤；部门管理员只看到公共库与本人管理的部门，普通用户请求返回 403；空态提示新建入口 | 新写 |
| 部门搜索框 | `GET /admin/departments` 返回结果前端过滤 | 按名称与编号即时过滤，数量到几十个时仍用同一列表，不切分页 | 新写 |
| 新建部门弹窗 | `POST /admin/departments` | 仅超级管理员可见入口；编号须符合 `[a-z0-9][a-z0-9_-]{0,127}`，名称 1 至 255 字；编号已存在时后端返回 200 与既有部门，前端按已存在处理，不当作新建成功 | 新写 |
| 部门详情 | `GET /admin/departments/{dept_id}` | 展示编号、名称、成员数、文档数；跨部门访问后端返回 404，前端按不存在处理，不提示无权限 | 新写 |

#### 6.10.2 部门数量变化时的部件行为

数量从几个变到几十个：列表接口无分页，返回全量。前端不做分页器，改为搜索框加前端过滤，列表本身滚动加载。部门数量到达上百个时再议服务端分页，在此之前不预设分页参数。

部门选择器一律动态拉取。上传目标库、认领目标库、例外授权目标部门、移动目标库这四处选择器，都从 `GET /admin/departments` 动态拉取，不得写死选项，不得缓存为常量。打开选择器时重新拉取，新增的部门立即出现。

扁平列表，不做层级树。后端 `Library` 模型没有父部门字段，部门之间是平级关系，不存在上下级。前端不画组织树，不按层级分组。

空态分两种。部门管理员名下无部门时列表为空态，提示联系超级管理员新建。超级管理员名下只有公共库与未分配库时同样给空态与新建入口。

#### 6.10.3 真实业务场景推演

新增部门：超级管理员建库，编号一旦创建不可改，建库时就要定好编号规则，建议与部门中文名对应，避免事后想改。新建后部门管理员任命与成员添加才可进行。

合并部门：后端没有合并接口。实际流程是先用移动审批把旧部门的文档逐批移进目标部门（`POST /moves`，走批准流程），再把成员逐一迁到目标部门，最后旧部门无成员无活文档时超级管理员删除。前端在移动请求页须展示源部门与目标部门，删除旧部门前须先校验并提示残留成员与文档数。

改名：后端没有部门改名接口，名称只在创建时写入。改名只能删除重建，而删除又要求无成员无活文档。前端不设改名入口。确需改名时走线下流程，先清空再重建，本评审不把改名排进部件清单。

停用：后端没有停用状态，部门只有存在与删除两种状态。停用部门的实际做法是移除全部成员并移走或删除全部文档，再删除部门。前端不设停用开关。已删除的部门在任何选择器中不再出现，历史审计事件保留部门编号，不随删除消失。

残留引用：文档的 `library_id` 指向已删除的部门不可能发生，因为删除被成员与活文档拦截。成员过期后读不到，续期须显式延长；过期成员的权限立即失效，下一次请求即生效，不用重新登录。前端在成员表展示有效期，过期行标为已过期并给续期入口。任命与移除即时生效，同样不用重新登录，因为每次请求都按 live 目录重建身份。

#### 6.10.4 管理员能力边界的界面区分

超级管理员：全部部门可见，可建库、可删库、可任免部门管理员、可授部门目标例外。

部门管理员：只看到公共库与本人管理的部门；只能在本人部门内加编者与读者、管理文件夹、授个人例外；看不到其他部门，也收不到其他部门存在的提示，后端返回 404，前端按不存在处理。

普通用户：看不到部门管理入口；可见库是公共库加本人所属部门库的并集，部门管理员还额外看到本人部门归属的项目库；提问与检索只在可见库内进行。

界面区分方式：入口按角色显示，看不到的入口直接不渲染，不用灰色禁用态冒充权限。越权操作后端返回 403 或 404 时，前端按无权限页或不存在处理，不泄露目标存在。部门管理员在本人部门内越权（例如任免部门管理员、授部门目标例外）后端返回 403，前端按无权限处理。

三组页面共用后台的无权限页与表格、弹窗、徽章组件，不新增基础组件。

## 7 样本示例偏差纠正

之前交付的 Pivot 样本示例与真实功能有五处偏差，本评审逐一纠正。

第一，样本示例的运营看板页不是真实功能。真实后台概览只有指标键值表与解析任务表，没有问答量柱状图、门禁结果环形图、运行事件流。指标字段尚未冻结，图表无数据来源。

第二，样本示例的成员与权限页不是真实功能。真实用户管理只有用户名、角色、状态三列与启用停用操作，没有四角色权限矩阵。角色只有管理员与普通用户两档。

第三，样本示例的系统设置页不是真实功能。Top-K、重排序、BM25 权重、门禁下限、预算上限、租约时长这些参数，前端没有对应的读取与写入接口。设置页整页删除，不保留。

第四，样本示例的模型切换与预算租约展示不是真实功能。模型由服务端配置，预算账本没有前端读取接口。样本示例里这三处是为演示编造的，不得带入正式前端。

第五，样本示例的成员与权限页把部门写成固定的四角色权限矩阵，是错的。真实的部门角色只有部门管理员、编者、读者三档，部门列表是动态拉取的，部门管理员只能管本人部门。样本示例里写死的部门与角色矩阵不得带入正式前端。

纠正方式是：样本示例保留为风格与交互参考，不作为功能清单。正式前端以第 6 节的清单为准。

## 9 风险与验收标准

商标风险：open-claude-ui 是 Claude 桌面端的高保真复刻。Pivot 对外产品不得原样照搬它的布局、配色组合、动效与品牌元素。验收时逐页核对：界面不得出现 Claude 的品牌标识与特征性布局，令牌值允许相近，整体观感必须属于问枢自己。

主题风险：两套主题必须同时通过同一批页面验收。验收项是：切换后无未适配的硬编码色值，文字与背景对比度在两套主题下都可读，焦点环在两套主题下都可见。`test-foundation.mjs` 的令牌断言必须覆盖两套主题。

接线风险：第二阶段的三组页面依赖后端接口的实际行为。审批、移动、部门库接口虽然已经实现，但前端接线前必须先跑通真实接口，确认字段与错误码，再写页面。不得按样稿的编造数据写死字段。

验收标准共五条。第一，现有 10 页在两套主题下全部可用，无样式回归。第二，主题切换一键生效，刷新后保持选择，首屏无闪烁。第三，问答全流程可用：提问、流式输出、引用查证据、澄清续答、取消、导出。第四，`npm run typecheck` 与 `npm run lint` 通过，`test-foundation.mjs` 通过。第五，GATE-P0 仍为未验证，本评审不改变验收状态，正式验收待 Owner 另行决定。
