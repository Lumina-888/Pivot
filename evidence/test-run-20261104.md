## 6. D8-05 三分支真实客户端复验

v1.0 记录的限制是「D8-05 文案只在 fake client 下验证，真实客户端异常类型不同」。本节用真实 minio 与 qdrant 客户端补上这一段。

方法：用 worker 镜像与同一份示例环境变量，`compose run --rm --no-deps` 覆盖桶名、集合名与 ensure 开关，直接调用 `worker/src/pivot_worker/assembly.py` 的 `_open_minio_store` 与 `_open_qdrant_store`。

| 场景 | 覆盖 | 实测输出 |
| --- | --- | --- |
| A 新鲜名称、ensure=0 | 桶与集合都不存在 | `RuntimeError: minio bucket pivot-probe-a-20261104 is missing (bucket missing, not unreachable); set PIVOT_MINIO_ENSURE_BUCKET=1 or create the bucket`；`RuntimeError: qdrant collection pivot_probe_a2_20261104 is missing (collection missing, not unreachable); set PIVOT_QDRANT_ENSURE_COLLECTION=1 or create the collection` |
| B 新鲜名称、ensure=1 | 允许自动创建 | 两侧均 `OK (opened)`，桶与集合被自动创建 |
| C 端点指向死端口、ensure=0 | 服务不可达 | `RuntimeError: minio is not reachable`；`RuntimeError: qdrant is not reachable` |

结论：三条分支在真实客户端下都正确，D8-05 的「缺失」与「不可达」不再混为一谈，ensure 开关也能真正建桶建集合。

清理：探针产生的桶 `pivot-probe-b-20261104` 已删除，集合 `pivot_probe_b_20261104` 已 `DELETE` 并返回 `{"result":true}`。

一次口径失误，记录备查：首次探测用了含大写的桶名 `pivot-probe-A-20261104`，真实客户端抛 `S3Error: code: InvalidBucketName`，导致误判为「缺失被报成不可达」。S3 桶名只允许小写，改用合法名称后结论正常。测试数据命名必须符合被测系统的命名规则，否则异常会被误读成产品缺陷。

### 10.3 新缺陷 D8-19：镜像内 API 反代恒为空表

`/login` 正常，但经 web 访问 API 全部失败：

| 请求 | 结果 | 响应体 |
| --- | --- | --- |
| `GET http://127.0.0.1:3000/login` | 200 | HTML 页面 |
| `GET http://127.0.0.1:3000/api/v1/healthz` | **404** | Next.js 的 HTML 404 页 |
| `GET http://127.0.0.1:8000/healthz`（api 直连） | 200 | `{"status":"ok"}` |
| 容器内 `env` | 有 `PIVOT_API_ORIGIN=http://api:8000` | — |
| 容器内 `/app/.next/routes-manifest.json` 的 `rewrites` | **`[]`** | — |

本地用 `PIVOT_API_ORIGIN=http://api:8000 npm run build` 构建出的 `web/.next/routes-manifest.json`，`rewrites` 里有 `"/api/v1/:path*" -> "http://api:8000/api/v1/:path*"`。同一份代码，差别只在构建时是否注入该变量。

因果验证：把带 rewrite 的 `routes-manifest.json` 拷进运行中的容器并重启，不改镜像与代码：

| 请求 | 注入前 | 注入后 |
| --- | --- | --- |
| `GET /api/v1/documents` | 404 HTML | **401 `application/json`** `{"code":"AUTH_INVALID_CREDENTIALS"，...}` |
| `GET /api/v1/healthz` | 404 HTML | 404 `application/json` `{"detail":"Not Found"}`（已透传到 api） |

结论：`next.config.mjs` 的 `rewrites()` 在**构建期**求值，`Dockerfile.web` 只在运行期由 compose 注入 `PIVOT_API_ORIGIN`，镜像里的反代表因此恒为空。真实后果是 web 容器的所有 `/api/v1/*` 调用 404，登录页与静态页正常，功能页全挂。

更值得记的是**测试全绿**：`test_NFR_OBS_compose_web.py` 6 项全过，因为它只断言镜像文本、compose 文本与 `/login` 可访问，不验证反代。这与 D8-03 的「纯文本断言绿灯但功能坏」是同一类问题。

建议修法（需 Owner 决策，本轮未改代码）：在 `Dockerfile.web` 的 `npm run build` 之前加 `ARG PIVOT_API_ORIGIN` 与 `ENV PIVOT_API_ORIGIN=${PIVOT_API_ORIGIN}`，并在 compose 的 `build.args` 传入；代价是反代目标在构建期被烘进镜像，换环境须重建。另一条路是把反代改为运行期读取的 route handler 或 middleware，改动更大且涉及 Next 结构。

### 10.4 新缺陷 D8-20：Playwright 夹具缺装配变量，起不来

```bash
PIVOT_REQUIRE_PLAYWRIGHT=1 pytest -q tests/integration/pipeline/test_NFR_UX_browser_ten_pages.py tests/integration/pipeline/test_FR_AUTH_001_browser_login.py
```

结果 `4 passed, 7 errors`，错误全部是同一个：`RuntimeError: timed out waiting for http://127.0.0.1:xxxxx/healthz: <urlopen error [Errno 111] Connection refused>`。

定位过程：夹具把 api 与 web 的 stdout/stderr 都指向 `DEVNULL`，看不到真因，于是按夹具的 env 手工起 api，逐步暴露两个缺失项：

| 缺失 | 报错 |
| --- | --- |
| `PIVOT_VECTOR_STORE=qdrant` | `RuntimeError: QA requires PIVOT_VECTOR_STORE=qdrant; the native QA path was removed (ADR-020)` |
| `PIVOT_BM25_K1`、`PIVOT_BM25_B` | `RuntimeError: PIVOT_BM25_K1 and PIVOT_BM25_B are required when PIVOT_RETRIEVAL_BACKEND=llama` |

时间线说明这不是一次性回归：夹具写于 2026-09-14（`3928753`），BM25 强制来自 2026-10-21（`e958e5b`），ADR-020 删除原生问答路径来自 2026-10-25（`3f89b86`）。也就是说 opt-in Playwright 至少自 10-21 起就无法启动，因为它默认 skip，CI 一直全绿。

诊断性问题：夹具吞掉子进程输出，真因被盖成 45 秒端口超时。建议夹具在启动失败时回读子进程日志并附进异常。

| --- | --- |
| 页面 URL | `/admin/users`（导航成功） |
| 管理接口响应 | 全部 403，符合预期 |
| 403 响应体 | `{"code":"AUTH_PASSWORD_CHANGE_REQUIRED"，"message":"首次登录或密码重置后必须先修改密码"}` |
| 页面内容 | 管理后台外壳（「用户管理」「新建用户」）正常渲染，无 ForbiddenView |
| 前端判定 | `isAdminForbidden` 要求 `status===403 且 envelope.code==="AUTH_FORBIDDEN"`，此码不匹配，页面落到 error 分支 |

判定：**测试口径过期，不是安全漏洞**。服务端仍然 403 阻断，数据没有返回；问题在于夹具种的新用户命中首登改密门禁（2026-10-22，`0a41733`），测试却假设首访即 `AUTH_FORBIDDEN`。修法二选一：夹具种用户后先走一次改密流程，或断言接受 `AUTH_PASSWORD_CHANGE_REQUIRED` 并另建一个已改密用户专测 RBAC 文案。

### 10.6 环境恢复

实验期间向运行中容器拷过 `routes-manifest.json`，结束时已 `--force-recreate` 从镜像重建，`/api/v1/documents` 复现 404 HTML，说明缺陷来自镜像本身、可稳定复现。探针用的一次性 Qdrant 集合（`pw_ten_20261104`、`pw_ten_20261104__llama__unassigned` 及几个 `pw_dbg*`）已全部删除，集合数回到 12 个既有集合。

## 11. 注意点

1. **本轮仍未验证 web 容器**。`next build` 成功不等于 `Dockerfile.web` 能构建、compose web 能起，也不等于 Playwright 十页可用。
2. **D8-05 的修复只在 worker 与 api 的装配入口验证**。真实链路上首次启动是否自动建桶建集合已确认，但并发首启、权限不足、桶名非法等异常路径未测。
3. **worker 镜像以 root 运行**。Celery 已告警 `SecurityWarning: ... superuser privileges`，属 fixture 限制，本轮未改，也不属于任何已登记缺陷。
4. **构建依赖网络姿势**。默认 bridge 网络下 `pip install` 会 ReadTimeout，需要 `--network=host` 加代理 build arg。这条只在本地成立，CI 与正式环境不适用，但不能当成「镜像一定能构建」的证据。
5. **`docker compose config` 的输出转义容易误读**。渲染结果里 `$$line` 是 config 的输出转义，容器内实际是 `$line`。判断探针是否被插值要看容器，不要只看 `config`。
6. **分组回归是 `--skip-web`**。前端四项里的 `npm test` 单独跑，未纳入 `run_grouped_tests.py`；全量口径仍缺 Playwright。
7. **85 项 skip 不等于通过**。db_pg 已单独补跑（50 passed），但 100k 容量、Playwright 十页、实时模型与 SSE 长连接仍是 opt-in，本轮未开启。
8. **D8-09 只规避未修复**。`db_pg` 用 `env -u DATABASE_URL` 绕开隐式覆盖，缺陷本身仍在。
9. **门禁不变**。本轮无一运行批准，`GATE-P0-001~008` 仍全部 unverified。任务 2 的 worker 起来只说明 fixture 能起，不满足 GATE-P0-008 的固定版本发布与回滚演练。
10. **web 容器能起但功能不可用**。`/login` 与静态页正常，`/api/v1/*` 全 404（D8-19）。看到容器 `healthy` 就判「web 通过」会误判。
11. **compose web 用例给了假绿灯**。6 项全过，但没有一项验证反代；新增断言建议：经 web 请求 `/api/v1/documents` 期望 `401 application/json`，出现 HTML 404 即失败。
12. **Playwright 的默认 skip 掩盖了夹具失效**。夹具自 2026-10-21 起就起不来，只在强制开启时才暴露（D8-20）。opt-in 开关不等于「随时能开」。
13. **Playwright 夹具吞掉了启动错误**。真因被盖成 45 秒端口超时，建议失败时回读子进程日志。
14. **本轮改动过运行中容器**（`docker cp` 注入 `routes-manifest.json`），已 `--force-recreate` 复原并复现缺陷；一次性 Qdrant 集合已删除。若后续有人在此环境继续测，应先确认容器来自镜像重建。

## 12. 建议

按收益排序，前三条能补齐当前最大的三个空白：

1. **修 D8-19（最高优先）**：它让 web 容器看起来健康、实际不能用。最小修法是 `Dockerfile.web` 在 `npm run build` 前接 `ARG`+`ENV PIVOT_API_ORIGIN`，compose 的 `build.args` 传入；同时给 `test_NFR_OBS_compose_web.py` 加一条反代断言，防再次「绿灯但功能坏」。
2. **修 D8-20**：给 Playwright 夹具补齐 qdrant 与 BM25 装配（或在 qdrant 不可用时明确 skip 并说明原因），并在启动失败时回读子进程日志，别再把真因盖成端口超时。
3. **修 D8-21**：夹具种完用户后先走改密，或拆成「未改密」与「已改密」两个用户分别断言。
4. **补缺陷 5、6 的端到端**（清单任务 4、5）：api 与 worker 都在跑，`/search` 的 BM25 腿与两类导出可实测，这是缺陷 5、6 唯一能写闭合的路径。
5. **修 D8-09**：`db_pg` 不该依赖 `DATABASE_URL` 的环境语义，建议夹具显式忽略该变量并加断言。
6. **补 worker 与 web 容器降权**：worker 以 root 跑已告警；web 同理。属 GATE-P0-008 的发布质量项。
7. **登记 Q5 探针预算的实测数据**：qdrant 恢复约 25 s，但本机已观测到建集合耗时 8 s 超过 `qdrant-client` 默认 5 s 超时的情形，历史集合更多时需补观测。

不建议现在做的：100k 容量与备份恢复（需要 staging 环境与 Owner 授权）、真实模型评测（需要供应商密钥与盲评设计）、GATE-P0 任何状态变更。
