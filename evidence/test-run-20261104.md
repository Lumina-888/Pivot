## 6. D8-05 三分支真实客户端复验

v1.0 记录的限制是「D8-05 文案只在 fake client 下验证，真实客户端异常类型不同」。本节用真实 minio 与 qdrant 客户端补上这一段。

方法：用 worker 镜像与同一份示例环境变量，`compose run --rm --no-deps` 覆盖桶名、集合名与 ensure 开关，直接调用 `worker/src/pivot_worker/assembly.py` 的 `_open_minio_store` 与 `_open_qdrant_store`。

| 场景 | 覆盖 | 实测输出 |
| --- | --- | --- |
| A 新鲜名称、ensure=0 | 桶与集合都不存在 | `RuntimeError: minio bucket pivot-probe-a-20261104 is missing (bucket missing, not unreachable); set PIVOT_MINIO_ENSURE_BUCKET=1 or create the bucket`；`RuntimeError: qdrant collection pivot_probe_a2_20261104 is missing (collection missing, not unreachable); set PIVOT_QDRANT_ENSURE_COLLECTION=1 or create the collection` |
| B 新鲜名称、ensure=1 | 允许自动创建 | 两侧均 `OK (opened)`，桶与集合被自动创建 |
| C 端点指向死端口、ensure=0 | 服务不可达 | `RuntimeError: minio is not reachable`；`RuntimeError: qdrant is not reachable` |

结论：三条分支在真实客户端下都正确，D8-05 的「缺失」与「不可达」不再混为一谈，ensure 开关也能真正建桶建集合。

清理：探针产生的桶 `pivot-probe-b-20261104` 已删除，集合 `pivot_probe_b_20261104` 已 `DELETE` 并返回 `{"result":true}`。

一次口径失误，记录备查：首次探测用了含大写的桶名 `pivot-probe-A-20261104`，真实客户端抛 `S3Error: code: InvalidBucketName`，导致误判为「缺失被报成不可达」。S3 桶名只允许小写，改用合法名称后结论正常。测试数据命名必须符合被测系统的命名规则，否则异常会被误读成产品缺陷。

### 10.3 新缺陷 D8-19：镜像内 API 反代恒为空表

`/login` 正常，但经 web 访问 API 全部失败：

| 请求 | 结果 | 响应体 |
| --- | --- | --- |
| `GET http://127.0.0.1:3000/login` | 200 | HTML 页面 |
| `GET http://127.0.0.1:3000/api/v1/healthz` | **404** | Next.js 的 HTML 404 页 |
| `GET http://127.0.0.1:8000/healthz`（api 直连） | 200 | `{"status":"ok"}` |
| 容器内 `env` | 有 `PIVOT_API_ORIGIN=http://api:8000` | — |
| 容器内 `/app/.next/routes-manifest.json` 的 `rewrites` | **`[]`** | — |

本地用 `PIVOT_API_ORIGIN=http://api:8000 npm run build` 构建出的 `web/.next/routes-manifest.json`，`rewrites` 里有 `"/api/v1/:path*" -> "http://api:8000/api/v1/:path*"`。同一份代码，差别只在构建时是否注入该变量。

因果验证：把带 rewrite 的 `routes-manifest.json` 拷进运行中的容器并重启，不改镜像与代码：

| 请求 | 注入前 | 注入后 |
| --- | --- | --- |
| `GET /api/v1/documents` | 404 HTML | **401 `application/json`** `{"code":"AUTH_INVALID_CREDENTIALS"，...}` |
| `GET /api/v1/healthz` | 404 HTML | 404 `application/json` `{"detail":"Not Found"}`（已透传到 api） |

结论：`next.config.mjs` 的 `rewrites()` 在**构建期**求值，`Dockerfile.web` 只在运行期由 compose 注入 `PIVOT_API_ORIGIN`，镜像里的反代表因此恒为空。真实后果是 web 容器的所有 `/api/v1/*` 调用 404，登录页与静态页正常，功能页全挂。

更值得记的是**测试全绿**：`test_NFR_OBS_compose_web.py` 6 项全过，因为它只断言镜像文本、compose 文本与 `/login` 可访问，不验证反代。这与 D8-03 的「纯文本断言绿灯但功能坏」是同一类问题。

建议修法（需 Owner 决策，本轮未改代码）：在 `Dockerfile.web` 的 `npm run build` 之前加 `ARG PIVOT_API_ORIGIN` 与 `ENV PIVOT_API_ORIGIN=${PIVOT_API_ORIGIN}`，并在 compose 的 `build.args` 传入；代价是反代目标在构建期被烘进镜像，换环境须重建。另一条路是把反代改为运行期读取的 route handler 或 middleware，改动更大且涉及 Next 结构。

## 11. 注意点

1. **本轮仍未验证 web 容器**。`next build` 成功不等于 `Dockerfile.web` 能构建、compose web 能起，也不等于 Playwright 十页可用。

8. **D8-09 只规避未修复**。`db_pg` 用 `env -u DATABASE_URL` 绕开隐式覆盖，缺陷本身仍在。
9. **门禁不变**。本轮无一运行批准，`GATE-P0-001~008` 仍全部 unverified。任务 2 的 worker 起来只说明 fixture 能起，不满足 GATE-P0-008 的固定版本发布与回滚演练。
10. **web 容器能起但功能不可用**。`/login` 与静态页正常，`/api/v1/*` 全 404（D8-19）。看到容器 `healthy` 就判「web 通过」会误判。
11. **compose web 用例给了假绿灯**。6 项全过，但没有一项验证反代；新增断言建议：经 web 请求 `/api/v1/documents` 期望 `401 application/json`，出现 HTML 404 即失败。
12. **Playwright 的默认 skip 掩盖了夹具失效**。夹具自 2026-10-21 起就起不来，只在强制开启时才暴露（D8-20）。opt-in 开关不等于「随时能开」。
13. **Playwright 夹具吞掉了启动错误**。真因被盖成 45 秒端口超时，建议失败时回读子进程日志。
14. **本轮改动过运行中容器**（`docker cp` 注入 `routes-manifest.json`），已 `--force-recreate` 复原并复现缺陷；一次性 Qdrant 集合已删除。若后续有人在此环境继续测，应先确认容器来自镜像重建。

### 12.3 D8-19：web 镜像内 API 反代恒为空表

**现象**：web 容器 `Up (healthy)`，`/login` 返回 200，但所有经 web 的 API 调用返回 Next 的 HTML 404 页；api 直连正常。

**复现**：

```bash
docker compose --env-file ops/compose.env.example --profile app up -d --build web
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' http://127.0.0.1:3000/api/v1/documents
# 实测：404 text/html
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/api/v1/documents
# 实测：401（api 正常，需要鉴权）
docker exec pivot-deps-web-1 sh -c "cat /app/.next/routes-manifest.json" | grep -o '"rewrites":\[[^]]*\]'
# 实测： "rewrites":[]
```

**根因**：`web/next.config.mjs:7` 的 `rewrites()` 在**构建期**求值，读取 `process.env.PIVOT_API_ORIGIN`；而 `Dockerfile.web:14` 的 `RUN npm run build` 执行时没有该变量，`docker-compose.yml:207-210` 的 `web.build` 也没有 `args`，只有运行期 `environment` 注入。构建产物里的反代表因此恒为空，运行期再注入无效。

**改法 A（推荐，最小改动）**：把变量在构建期传进镜像。

`Dockerfile.web`（在第 14 行 `RUN npm run build` 之前插入）：

```dockerfile
COPY web /app

# D8-19: next.config.mjs 的 rewrites() 在构建期求值，构建时必须拿到
# PIVOT_API_ORIGIN，否则镜像里的 routes-manifest.json 反代表为空，
# 运行期由 compose 注入无法补救。
ARG PIVOT_API_ORIGIN
ENV PIVOT_API_ORIGIN=${PIVOT_API_ORIGIN}

RUN npm run build
```

`docker-compose.yml` 的 `web.build`：

```yaml
    build:
      context: .
      dockerfile: Dockerfile.web
      args:
        PIVOT_API_ORIGIN: ${PIVOT_API_ORIGIN:?set PIVOT_API_ORIGIN}
```

代价：反代目标被烘进镜像，换 origin 必须重建镜像。这一点要写进 `Dockerfile.web` 的注释与 `ops/compose-intent.md`。

**改法 B（结构性改动，需 ADR）**：把反代改成运行期读取 env 的 Route Handler 或 Middleware，镜像与配置解耦。改动面大于 A，且要重新评估 `tests/e2e` 与 `web/features` 的调用路径，建议单独开切片。

**验收**（改完后三条同时成立）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/login                  # 200
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' http://127.0.0.1:3000/api/v1/documents
                                                                                       # 401 application/json
docker exec pivot-deps-web-1 sh -c "cat /app/.next/routes-manifest.json" | grep -c '"/api/v1/:path\*"'  # 1
```

**应补的回归测试**（加进 `tests/integration/pipeline/test_NFR_OBS_compose_web.py`，命名与风格照该文件现有 `_reachable` 与 `PIVOT_REQUIRE_COMPOSE_WEB` 开关）：

```python
def test_NFR_OBS_compose_web_proxies_api_when_running():
    """D8-19: 反代在构建期固化。容器 healthy 不等于反代生效，
    云原生 404 页（text/html）与 api 的 JSON 401 必须区分开。"""
```

断言要点：`/api/v1/documents` 的状态码为 401，而非 404；`content-type` 含 `application/json`；出现 `text/html` 即失败。

**注意**：`test_NFR_OBS_compose_web_injects_api_origin_without_production_url` 现有断言是「compose 的 web 段不得写死 `https?://` 开头」与「不得出现 `NEXT_PUBLIC_`」，加 `build.args` 后仍然满足，不要顺手把 URL 写死进 compose。另外 `next build` 在本机不带该变量也能成功，只是产出空反代表，所以「构建成功」不能作为修复生效的证据。

### 12.4 D8-20：Playwright 夹具起不来

**现象**：`PIVOT_REQUIRE_PLAYWRIGHT=1` 跑十页与登录用例，得到 `4 passed / 7 errors`，错误全部是 `RuntimeError: timed out waiting for http://127.0.0.1:xxxxx/healthz: <urlopen error [Errno 111] Connection refused>`。

**复现**：

```bash
PIVOT_REQUIRE_PLAYWRIGHT=1 PYTHONPATH=api/src:worker/src \
  .venv/bin/python -m pytest -q tests/integration/pipeline/test_NFR_UX_browser_ten_pages.py
```

**根因**：`tests/integration/pipeline/browser_login_support.py:185` 的 `api_env.update({...})` 只给 memory 装配，缺三项：

| 缺失变量 | 缺失后报错 |
| --- | --- |
| `PIVOT_VECTOR_STORE=qdrant` 与 `PIVOT_QDRANT_*` | `RuntimeError: QA requires PIVOT_VECTOR_STORE=qdrant; the native QA path was removed (ADR-020)` |
| `PIVOT_BM25_K1`、`PIVOT_BM25_B` | `RuntimeError: PIVOT_BM25_K1 and PIVOT_BM25_B are required when PIVOT_RETRIEVAL_BACKEND=llama` |

夹具写于 2026-09-14（`3928753`），BM25 强制来自 2026-10-21（`e958e5b`），ADR-020 来自 2026-10-25（`3f89b86`），因此该夹具至少自 10-21 起无法启动。

**次生问题**：`api` 与 `web` 两个子进程的 `stdout`、`stderr` 都指向 `subprocess.DEVNULL`，真因被盖成 45 秒端口超时，排查成本高。

**改法**：

1. 补装配变量。在 `api_env.update({...})` 中追加：

   ```python
   "PIVOT_VECTOR_STORE": "qdrant",
   "PIVOT_EMBEDDING": "hash",
   "PIVOT_BM25_K1": "1.2",
   "PIVOT_BM25_B": "0.75",
   "PIVOT_QDRANT_ENDPOINT": os.environ.get("PIVOT_QDRANT_ENDPOINT", "127.0.0.1:6333"),
   "PIVOT_QDRANT_COLLECTION": "pivot_playwright",
   "PIVOT_QDRANT_VECTOR_SIZE": "8",
   "PIVOT_QDRANT_DISTANCE": "Cosine",
   "PIVOT_QDRANT_ENSURE_COLLECTION": "1",
   ```

2. 启动前探测 Qdrant，不可达时明确 `pytest.skip` 并写明原因，不要让它退化成 45 秒超时。
3. 子进程输出改写到 `tempfile`，健康检查超时时把日志尾部附进异常消息。
4. `ops/run_playwright_login.py` 只是转发 pytest，改夹具即可，无需改该脚本。

**验收**：

```bash

  .venv/bin/python -m pytest -q tests/integration/pipeline/test_FR_AUTH_001_browser_login.py
# 本轮补齐装配变量后实测 4 passed（50.01 s）
```

### 12.5 D8-21：RBAC 浏览器用例口径过期

**现象**：补齐 D8-20 后，十页 `6 passed / 1 failed`，失败项为 `test_FR_RBAC_001_browser_regular_user_admin_is_forbidden`，超时等待文案「无权限访问管理后台」。

**实测证据**：页面正常导航到 `/admin/users`，管理接口全部 403，但响应体是：

```json
{"code":"AUTH_PASSWORD_CHANGE_REQUIRED","message":"首次登录或密码重置后必须先修改密码","request_id":"...","retryable":false}
```

前端 `web/features/admin/rbac.ts:3` 的 `isAdminForbidden` 要求 `status === 403` 且 `envelope.code === "AUTH_FORBIDDEN"`，此码不匹配，页面落到 error 分支，不渲染 `ForbiddenView`。

**判定**：测试口径过期，不是安全漏洞。服务端仍然 403 阻断，管理数据没有返回。首登改密门禁来自 2026-10-22（`0a41733`），晚于夹具编写时间。

**改法 A（推荐）**：夹具种完用户后先改密。

```bash
# 以该用户登录取得 access token，再调用（路由见 api/src/pivot/auth/http.py:131）
POST /api/v1/auth/change-password
Authorization: Bearer <token>
{"current_password": "<初始密码>", "new_password": "<新密码>"}   # 返回 204
```

改密后建议重新登录再继续断言；是否轮换 token 由 M01 的实现决定，改完自行确认。

**改法 B**：保留「未改密用户」用例，但把断言改成接受 `AUTH_PASSWORD_CHANGE_REQUIRED` 的提示页，另建一个已改密用户专测 `AUTH_FORBIDDEN` 与 `ForbiddenView`。B 的覆盖更全，推荐 B 或 A+B 组合。

**验收**：`PIVOT_REQUIRE_PLAYWRIGHT=1 ... test_NFR_UX_browser_ten_pages.py` 期望 7 passed。

### 12.6 顺带项

- **D8-09**：`tests/integration/db_pg/conftest.py` 不应受 `DATABASE_URL` 影响，建议在夹具里显式忽略该变量，并加一条断言。本轮用 `env -u DATABASE_URL` 规避，缺陷本身未修。

## 13. 建议

第 12 节是可直接执行的修复指引，本节只排优先级。前三条对应三个新缺陷，也是当前收益最高的三件事：

1. **修 D8-19（最高优先）**：它让 web 容器看起来健康、实际不能用。最小修法是 `Dockerfile.web` 在 `npm run build` 前接 `ARG`+`ENV PIVOT_API_ORIGIN`，compose 的 `build.args` 传入；同时给 `test_NFR_OBS_compose_web.py` 加一条反代断言，防再次「绿灯但功能坏」。
2. **修 D8-20**：给 Playwright 夹具补齐 qdrant 与 BM25 装配（或在 qdrant 不可用时明确 skip 并说明原因），并在启动失败时回读子进程日志，别再把真因盖成端口超时。
3. **修 D8-21**：夹具种完用户后先走改密，或拆成「未改密」与「已改密」两个用户分别断言。
4. **补缺陷 5、6 的端到端**（清单任务 4、5）：api 与 worker 都在跑，`/search` 的 BM25 腿与两类导出可实测，这是缺陷 5、6 唯一能写闭合的路径。
5. **修 D8-09**：`db_pg` 不该依赖 `DATABASE_URL` 的环境语义，建议夹具显式忽略该变量并加断言。
6. **补 worker 与 web 容器降权**：worker 以 root 跑已告警；web 同理。属 GATE-P0-008 的发布质量项。
7. **登记 Q5 探针预算的实测数据**：qdrant 恢复约 25 s，但本机已观测到建集合耗时 8 s 超过 `qdrant-client` 默认 5 s 超时的情形，历史集合更多时需补观测。

不建议现在做的：100k 容量与备份恢复（需要 staging 环境与 Owner 授权）、真实模型评测（需要供应商密钥与盲评设计）、GATE-P0 任何状态变更。
