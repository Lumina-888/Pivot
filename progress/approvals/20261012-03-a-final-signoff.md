## 签认项 3/7: M01 / 安全

**责任**: 确认鉴权与安全策略

### 确认要点:

#### 3.1 owner-only 策略
- ✅ **确认**: 只有 Run owner 可以恢复
- ✅ **确认**: 管理员**没有**代理恢复权限
- **理由**: 澄清回复可能包含敏感业务信息，必须严格限制

#### 3.2 不可见 Run 的 404 统一响应
- ✅ **确认**: 不存在/不可见/他人 Run 均返回 404，不泄露存在性
- ✅ **确认**: 不先返回 state 或 clarification 信息
- **理由**: 防止通过错误响应差异推断 Run 存在性

#### 3.3 停用用户的鉴权重检
- ✅ **确认**: 同键重放时重新验证 Bearer/active/token_version
- ✅ **确认**: 受理后用户停用/会话删除，重放仍拒绝
- **理由**: 不能用历史成功回执绕过当前鉴权状态

#### 3.4 输入验证规则
- ✅ **确认**: `answer` 最大 10,000 字符
- ✅ **确认**: 拒绝控制字符（如 `\x00`, `\x1F` 等）
- ✅ **确认**: 严格拒绝额外字段
- **建议**: 额外拒绝过长的单行（如超过 1000 字符无换行）

#### 3.5 敏感 prompt 的公开投影
- ✅ **确认**: `prompt` 不包含:
  - 原始 reasoning
  - 工具参数
  - 受保护证据内容
  - 其他 Run 的存在性线索
- **建议**: 服务端生成 prompt 时使用白名单模板，不直接公开 LangGraph interrupt value

## 签认项 4/7: M03 / 数据与事务

**责任**: 确认持久化与事务协议

### 确认要点:

#### 4.1 幂等命名空间
- ✅ **确认**: `(principal_id, run_id, operation=resume, idempotency_key)` UNIQUE
- ✅ **确认**: 与创建 Run 的幂等键空间隔离
- **理由**: 同一 Run 可能有多个操作（create/resume/cancel），需要独立命名空间

#### 4.2 精确值绑定
- ✅ **确认**: 绑定解码后的 `(clarification_id, answer)` 精确值
- ✅ **确认**: 不 trim/Unicode 归一化/改变大小写
- ⚠️  **建议**: 使用结构化序列化（如固定顺序 JSON）+ SHA256 作索引，但保留原始值用于比较
- **原因**: 防止哈希碰撞导致的误判

#### 4.3 单次受理的条件事务
- ✅ **确认**: 每 `(run_id, clarification_id)` 最多一个有效受理
- ✅ **确认**: 条件转移 `waiting_for_user → resuming` 与受理记录在同一事务
- ✅ **确认**: 事务失败不返回 202
- **理由**: 保证原子性，避免状态不一致

#### 4.4 执行意图持久化
- ✅ **确认**: 受理成功后持久化可重放执行意图
- ⚠️  **注意**: 当前使用 BackgroundTasks，不保证崩溃恢复
- **04-A 边界**: 真正的持久化执行意图队列由 04-A 设计（ExecutionIntent 表）

## 签认项 5/7: M05 / 状态与预算

**责任**: 确认 Run 状态管理与预算逻辑

### 确认要点:

#### 5.1 interrupt ID 与 thread 绑定
- ✅ **确认**: `clarification_id` 由服务端生成，绑定唯一的 LangGraph interrupt
- ✅ **确认**: 不可猜测，不能用它绕过 owner 鉴权
- ✅ **确认**: 第二轮 interrupt 禁止（只允许一次澄清）

#### 5.2 状态回执与实时状态分离
- ✅ **确认**: HTTP 202 返回 `state=resuming`（历史受理状态）
- ✅ **确认**: 客户端通过 GET/SSE 获取实时状态（retrieving/completed 等）
- **理由**: 202 只表示受理成功，不保证已执行或执行完成

#### 5.3 累计预算不清零
- ✅ **确认**: 恢复后预算、已消耗 rewrite/clarification 次数、截止时间不重置
- ✅ **确认**: 预算耗尽时安全终止（failed/refused/uncertain）
- **理由**: 避免通过恢复绕过预算限制

#### 5.4 取消与恢复的竞争
- ✅ **确认**: 取消优先（取消先提交则恢复失败；恢复先提交则取消幂等读终态）
- ✅ **确认**: 已终态的 Run 不能被恢复覆盖
- **理由**: 保护终态的不可变性

#### 5.5 错误优先级
- ✅ **确认**: 鉴权/不可见 → 已受理键冲突 → 终态/时限 → 状态/澄清ID → 其他门禁
- **理由**: 不泄露业务信息，先检查权限再检查业务状态
