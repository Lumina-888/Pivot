## 第 3 项：M01 / 安全

### 签认内容
owner-only、不可见404、停用/重放鉴权、输入/外发与敏感prompt规则

### 关键决策点

#### 3.1 授权边界
**提案**:
1. 只有 Run 的 owner 可以回复澄清
2. 管理员**没有**代理恢复权限
3. 非 owner / 不存在 / 不可见统一返回 404（不泄露存在性）

**决策**:
- [ ] **接受** owner-only 策略（管理员无特权）
- [ ] 确认 404 统一文案（不区分"不存在"vs"无权限"）

#### 3.2 重放鉴权
**提案**: 同键重放历史回执时，重新检查用户 active/token_version

**场景**: 用户提交回复后被停用，随后用同样的 idempotency_key 重试
- 已成功受理的回执可以重放（202）
- 但如果当前用户已停用，拒绝返回回执

**决策**:
- [ ] **接受** 重放时重新鉴权
- [ ] 确认不能用旧的鉴权快照授权重放

#### 3.3 输入验证与限制
**提案**: `answer` 字段验证规则
- 最大长度: 10,000 字符（已批准）
- 禁止控制字符（除 `\n` / `\t`）
- 禁止非 UTF-8 合法字符
- 禁止嵌入二进制数据

**决策**:
- [ ] **接受** 这些输入验证规则
- [ ] 确认超出限制返回 422 且不反射用户输入内容

#### 3.4 敏感信息保护
**提案**: `clarification.prompt` 的公开投影必须过滤
- ❌ 不能包含: 原始 reasoning / Prompt / 工具参数 / 受保护证据 / 存在性线索
- ✅ 只包含: 经服务端验证、长度限制的安全公开文本

**决策**:
- [ ] **接受** 这些脱敏规则
- [ ] 确认不直接公开 LangGraph interrupt value

## 第 4 项：M03 / 数据基础

### 签认内容
单次受理/幂等命名空间、条件事务、执行意图与04-A/DR-011边界

### 关键决策点

#### 4.1 幂等命名空间设计
**提案**: 幂等键设计
```
(principal_id, run_id, operation=resume, idempotency_key) UNIQUE
```

与创建 Run 的幂等键空间隔离（operation 不同）

**绑定**: 解码后的 `(clarification_id, answer)` 精确值
- 同键同参 → 重放 202
- 同键异参 → 409 IDEMPOTENCY_CONFLICT

**决策**:
- [ ] **接受** 这个幂等命名空间设计
- [ ] 确认使用结构化序列化摘要（不是字符串拼接）

#### 4.2 单次受理协议
**提案**: 每个 `(run_id, clarification_id)` 最多一个有效受理
- 同键并发竞争：只有一个受理成功，其他返回 409
- 不同键并发（即使 answer 相同）：只有一个受理，失败者 409

**决策**:
- [ ] **接受** 单次受理保证
- [ ] 确认使用数据库条件事务（不是进程内锁）

#### 4.3 受理事务边界
**提案**: 受理事务原子记录
1. 唯一回复/幂等映射
2. 条件转移 `waiting_for_user → resuming`
3. 可重放执行意图

事务失败 → 不返回 202

**决策**:
- [ ] **接受** 这个事务边界定义
- [ ] 确认 HTTP 返回 202 不保证外部调用一定启动（执行者消费意图）

#### 4.4 与 04-A 的边界
**提案**: 
- 03-A 负责: 受理事实 / 幂等回执 / 执行意图持久化
- 04-A 负责: checkpoint / 租约 / fencing / 崩溃恢复

**决策**:
- [ ] **接受** 这个职责分界
- [ ] 确认 03-D 的 InMemorySaver 只能证明开发夹具行为，生产持久化需要 04-A

## 第 5 项：M05 / ReAct/QA/Run/SSE

### 签认内容
interrupt ID/原thread、状态/回执分离、累计预算/取消、错误优先级

### 关键决策点

#### 5.1 interrupt 机制
**提案**:
- 服务端生成不可猜测的 `clarification_id`
- 绑定该 Run 的唯一一次有效 interrupt
- 不能用它绕过 owner 鉴权
- 使用服务端 `thread_id`（客户端不提供）

**决策**:
- [ ] **接受** 这个 interrupt ID 设计
- [ ] 确认服务端 thread_id 不作为客户端授权参数

#### 5.2 状态与回执分离
**提案**:
- 202 回执中的 `state=resuming` 是**历史受理时刻状态**
- 客户端通过 GET/SSE 获取**实时状态**（retrieving/终态）
- 同键重放返回同一 receipt，但 request_id 新生成

**决策**:
- [ ] **接受** 状态/回执分离设计
- [ ] 确认回执不含答案/证据、attempt/thread/租约信息

#### 5.3 累计预算不清零
**提案**: 恢复后
- run_id / message_id 保持原值（不创建新 Run）
- 预算、已消耗 rewrite/clarification 次数不重置
- 原问题 / scope 不改变
- 截止时间（deadline）不延长

**决策**:
- [ ] **接受** 预算累计行为
- [ ] 确认预算耗尽时安全终止（failed/refused），不能发布未验证正文

#### 5.4 取消与恢复的竞争
**提案**: 优先级
1. 已受理后取消仍可获胜（取消检查在模型/工具/提交边界重复执行）
2. 晚到结果不能覆盖终态
3. 取消先提交 → 结果 CAS 失败
4. 结果先提交 → 取消幂等读终态，不改答案

**决策**:
- [ ] **接受** 取消优先的竞争策略
- [ ] 确认使用数据库 fencing/state_version（不是进程内判断）

#### 5.5 错误判定优先级
**提案**: 错误检查顺序
1. 鉴权/不可见（401/403/404）
2. 已受理键重放或冲突（202/409 IDEMPOTENCY_CONFLICT）
3. 新键终态/时限（409 RUN_CANCELLED / RUN_TIMEOUT）
4. 状态/澄清ID（409 RESUME_NOT_ALLOWED / CLARIFICATION_MISMATCH）
5. 其他恢复门禁（预算/资源/版本）

**决策**:
- [ ] **接受** 这个错误优先级顺序
- [ ] 确认不能通过重试绕过拒绝

**提案**:
- 用户点击"提交"后，客户端生成 `idempotency_key`（如 UUID）
- 网络超时/断线重试时，使用**同样的 key**
- SSE 重连**不会**重新提交 resume

**决策**:
- [ ] **接受** 这个幂等重试逻辑
- [ ] 确认重连只是重新订阅事件，不触发新的执行

#### 6.3 202 历史回执处理
**提案**: 同键重放返回 202 时
- 客户端识别 `state=resuming`（历史状态）
- 不重复显示"正在处理"动画
- 通过 SSE 或轮询 GET 获取实时状态

**决策**:
- [ ] **接受** 这个回执处理逻辑

#### 6.4 错误码消费

- 409 RESUME_NOT_ALLOWED → 提示"无法恢复此对话"

- 422 INVALID_RESUME_REQUEST → 提示"输入无效"
- 已知其他 4xx/5xx → 通用错误提示

**决策**:
- [ ] **接受** 这些错误码的前端处理
