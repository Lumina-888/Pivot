# ADR-019：审批流

- 状态：已接受；Owner 2026-10-25 批准。五个开放问题已全定。
- Accountable：M01；Contributors：M02、M03、M04、M10。
- 基线：main（ADR-017、ADR-018 已接受并落 main）。
- 需求：FR-RBAC-004 的 P1-3 部分。
- 依据：ADR-016 的 D7；ADR-017；ADR-018 的 D4、D5。

## 背景与范围

P1-1 已经落地库级隔离。文档只归属一个库。库是公共库或部门库。用户可见库是公共库加所属部门库之并集。检索按库分集合执行过滤。管理 API 与审计已经覆盖部门与成员变更。

P1-2 已经定下例外与临时授权。文档级例外可以破例共享单篇文档。临时授权可以带到期时间。到期自动收回。续期在到期前直接改到期时间。

P1-4 已经定下文件夹与项目库。部门库内再分项目文件夹。项目等于独立项目库。项目文档进入分认领与跨库移动两路。跨库移动一路随 P1-3 设计。

P1-3 补三件能力。第一件是发布审批。上传不等于发布。第二件是跨库移动审批。移动须审批。第三件是上传时选库。上传者可以选目标库。

本稿不含前端审批页面。页面细节由前端切片定。本稿不含自动审批规则。按内容自动放行不在本稿范围。自批直通按角色定。自批直通不属于自动审批规则。

审批目标只到库一级。文件夹归属不在审批范围。文件夹归属由文件夹管理定。审批通过后文档落在目标库默认文件夹。目标库内文件夹归属事后由文件夹管理定。

## 决策 D1 发布审批

版本状态机补充待审批态。新状态是 pending_approval 与 rejected。两状态加入 STATES。新增四条转移。pending_approval 经 approve 到 uploaded。pending_approval 经 reject 到 rejected。pending_approval 经 withdraw 到 uploaded。rejected 经 resubmit 到 pending_approval。删除仍可终结 rejected 版本。

上传带目标库时版本进入待审批态。版本不进入流水线。工作线程不拉取待审批版本。prepare_ingest 只接受 uploaded 与 queued。待审批态天然被排除。即使调用也无动作。路由层同样跳过 ingest 调用。两层共同保证待审批文档不进入解析。

待审批文档库归属保持未分配。审批通过时才改写目标库。这一点是强制要求。预览与下载路径只按库可见性判定。路径不检查版本状态。提前写目标库会把原文漏给目标库成员。保持未分配才能堵住这条路。

审批通过后版本进入正常流水线。版本经 approve 到 uploaded。审批服务触发 ingest 调用。流水线依次解析、索引。版本成为 ready 且 current 后可检索。索引写入目标库集合。写入时库归属已经是目标库。

审批人按目标库定。部门库由部门管理员批。公共库由总管理员批。项目库由项目负责人批。项目库审批人按层级类推。类推随本稿接受而定。

审批拒绝后版本进入 rejected。文档保持未分配。请求关闭并记录理由。上传者可以重提。重提经 resubmit 到 pending_approval。重提可以换目标库。上传者也可以放弃。放弃后走现有删除流程。

待审批队列对审批人可见。部门管理员看本部门目标队列。项目负责人看本项目目标队列。总管理员看全局队列。上传者看本人提交与结果。队列项包括文档标识、标题、上传者、目标库、提交时间、状态。待审批文档详情走队列路径。详情不走普通详情路径。

复核读是专用读路径。复核读不走预览与下载路径。复核读允许上传者本人。复核读允许目标库审批人。复核读允许总管理员。复核读从隔离存储取原文。复核读写入审计事件。事件名为 doc.approval.review。

自批直通按角色定。上传者即目标库审批人时请求立即通过。请求事件与通过事件齐全。请求不在队列等待。部门管理员上传到本部门库直通。项目负责人上传到本项目库直通。总管理员上传到公共库直通。普通成员上传必须排队。

## 决策 D2 上传时选库

上传时上传者选择目标库。目标库参数可选。不选沿用现行行为。现行行为是默认落未分配库。现行行为走认领路径。认领路径见 D4。

目标库必须存在。目标库必须在上传者权限内。部门库目标须是本部门库。上传者须是本部门成员。上传者须有上传权限。上传权限见 ADR-017 D5。项目库目标须是我加入的项目库。上传者须是项目成员。上传者须有上传权限。目标库不可是未分配库。未分配不是目标。

不可见的目标库按不存在处理。跨部门目标返回不存在。不提示存在性。规则与认领一致。目标库校验在上传时执行。校验失败拒绝上传。不创建待审批版本。

重复上传返回已有版本。重复上传不产生新请求。上传者可以在审批前改目标库。改目标写审计事件。改目标不产生新请求。

公共库目标已定（Owner 2026-10-25）：允许选。允许选则进入总管理员队列。

上传选库依赖 P1-2 上传门禁。现行上传路由只允许总管理员。ADR-017 D5 把上传门禁列为 P1-2 实现项。P1-3 的选库建立在门禁之上。门禁先落地，选库才有上传者人群。

## 决策 D3 跨库移动审批

移动提议人按源库范围定。部门管理员提议本部门库文档移出。项目负责人提议本项目库文档移出。总管理员提议任意文档移出。普通成员不能提议移动。文件夹全权不能提议跨库移动。跨库移动是库级管理动作。

审批人是目标库管理员。部门库由部门管理员批。公共库由总管理员批。项目库由项目负责人批。单边审批已定（Owner 2026-10-25）。单边理由是风险在获得方。获得方成员新见文档。源库失去文档不是披露。双边未采纳。

移动请求是独立记录。记录不改动版本状态。文档在源库保持 ready。源库成员继续正常可见。请求字段包括文档标识、源库、目标库、提议人、审批人、状态、理由、时间。审批人按角色取队列。不指派到个人。同角色审批人都可行动。行动人记入决策事件。

一文档只能有一个未决移动请求。第二提议直接拒绝。提议时文档必须未删除。已删除文档提议返回不存在。提议目标必须是已发布文档。未分配文档没有移动可言。

审批通过后执行移动。执行改写文档库归属。执行调用调和入口。调和重建目标库集合节点。调和清扫其余集合同文档节点。调和入口复用 P1-2 D3。调和失败重试并对管理员可见。失败状态字段由开发计划定。

移动后文档落在目标库默认文件夹。目标库内文件夹归属事后定。文件夹归属由文件夹管理定。移动不改变文档例外。例外是文档级授权。例外与库归属独立。移动后例外继续有效。

审批拒绝后文档留在原库。原库可见性不变。请求关闭并记录理由。提议人可以再次提议。再次提议是新请求。再次提议重新排队。提议人可以撤回未决移动提议。撤回后文档留在原库。

回滚定义为对称的再次审批移动。移回去同样走审批。回滚不另设特殊路径。回滚请求理由写明回滚。回滚请求关联原执行事件。审计链把两次移动关联起来。紧急回滚靠总管理员自批。总管理员自批全部是设计允许的。

## 决策 D4 与认领的衔接

认领与审批是单通道。同一文档不得双通道。通道按文档状态分。普通未分配文档走认领。带未决请求的文档走审批队列。认领拒绝带未决请求的文档。拒绝覆盖发布请求与移动请求。移动请求文档本就不在未分配库。认领本来碰不到移动请求文档。发布请求文档是认领必须拒绝的情形。

认领必须检查未决请求。发现未决请求时拒绝认领。检查是新增要求。现行认领只检查库归属。现行认领不检查请求状态。开发计划必须补上检查。

总管理员认领是快车道。认领本身即审批。认领不走审批队列。快车道只针对普通未分配文档。带未决发布请求的文档不在快车道内。总管理员同样先走队列。队列审批后文档进入目标库。

部门管理员认领到本部门库是自批。认领人即本部门库审批人。认领即自批。认领允许并写审计。审计事件沿用 authz.library.claim。认领不产生审批队列记录。项目负责人认领到本项目库同理。项目认领依赖 P1-4 模型落地。项目类型与项目成员模型先落地。模型落地前项目认领路径不启用。

部门管理员认领不得绕过队列。待审批文档目标是本部门库时同样拒绝认领。认领人即使是审批人也拒绝。单通道保证审计轨迹唯一。审批轨迹与认领轨迹不得混淆。

删除取消未决请求。删除是 tombstone 优先。请求关闭为已取消。取消事件记入审计。已删除文档的新提议返回不存在。规则与认领一致。

例外不得授予待审批文档。待审批文档尚未发布。例外目标必须是已发布文档。审批通过后例外正常授予。规则防止例外通道漏出待审批文档。

已发布文档的新版本跳过审批。范围没有变化。审批是范围门禁。不是内容质量评审。新版本内容敏感度回退走下线流程。下线流程是现有删除语义。本条是设计决定。Owner 复核时可以推翻。

## 决策 D5 审批的性质

审批是范围与敏感度门禁。审批判断文档可不可以对目标库成员可见。审批不判断文档写得好不好。写作质量不是拒绝理由。拒绝理由应当围绕范围。拒绝理由应当围绕敏感度。典型理由是含有未脱敏内部信息。典型理由是目标库成员不应见此文档。

审批人不需领域专长。审批人只需判断可见范围。范围判断依据是目标库成员构成。范围判断依据是文档敏感程度。判断标准应当写入审批指南。指南由运营定。本稿不定指南内容。

## 决策 D6 审计

审批事件全部走 append-only 审计。审计只追加，不修改。审计失败时操作拒绝。规则与 ADR-017 D4 一致。PG 路径走同一数据库会话事务。决策与库改写同生同灭。

事件名沿用现有风格。发布请求事件是 doc.approval.requested。撤回事件是 doc.approval.withdrawn。通过事件是 authz.approval.approved。拒绝事件是 authz.approval.rejected。移动提议事件是 doc.move.proposed。移动执行事件是 authz.library.move。取消事件是 doc.move.cancelled。复核读事件是 doc.approval.review。代批事件是 authz.approval.delegated，审批人记代批人。总管理员可设多个。admin 角色可授予多人。每个审批、代批动作审计均记操作管理员。

审计元数据带文档标识。元数据带源库与目标库。元数据带提议人与审批人。元数据带所属部门标识。元数据带项目标识。部门视图按部门标识过滤。项目视图按项目标识过滤。缺失标识会让视图漏掉事件。

队列与历史对审批人可见。部门管理员看本部门队列与历史。项目负责人看本项目队列与历史。总管理员看全局队列与历史。上传者看本人提交与结果。越权尝试进报表。

撤回是上传者权利。上传者可以撤回未决发布请求。撤回后版本回到 uploaded。撤回后流水线按现行行为进行。撤回后文档进入未分配 ready。撤回后分发走认领路径。撤回事件记入审计。撤回不是拒绝。撤回不产生拒绝记录。

## 非目标

本稿不改 P1-1 已落地的库模型。库标识与集合命名保持不变。审批态落在版本状态机。文档行不新增状态字段。审批请求记录的存储结构留开发计划定。

本稿不碰 DR-010 数值。本稿不立新的生产装配默认值。本稿不改单智能体架构。本稿不改答案层门禁默认状态。本稿不含前端审批页面。本稿不含自动审批规则。本稿不做文件夹级审批。审批目标只到库一级。

## 风险与残余

待审批文档绝不能经检索漏出。防护分四层。第一层是版本状态。待审批态不在可检索态内。可检索态只有 ready。第二层是向量与 chunk。待审批文档没有向量。待审批文档没有已发布 chunk。第三层是库归属。待审批文档保持未分配。未分配只对总管理员可见。第四层是列表过滤。列表只展示 current 且 ready 版本。测试必须覆盖四层。测试包括检索、引用、预览、下载、列表。

审批队列可能积压。没有 SLA 时文档长期挂起。缓解办法是审批人看板。看板展示请求老化。缓解办法是总管理员代批。代批权限见开放问题。缓解办法是上传者撤回。撤回回到认领路径。

移动调和失败会滞后。滞后是可用性损失。滞后不是保密损失。授权钩子按实时库归属判定。旧集合残留向量不会被未授权者拿到。目标库成员在调和完成前搜不到文档。失败状态必须对管理员可见。失败重试必须有上限。上限与告警阈值留开发计划定。

自批边界已经定下。部门管理员自批本部门库。项目负责人自批本项目库。总管理员自批全部。普通成员自批不允许。自批直通按角色定。自批直通不按内容定。自批直通不属于自动审批规则。

实施顺序有两处依赖。第一处是 P1-2 上传门禁。门禁先落地，选库才有上传者人群。第二处是 P1-4 项目模型。项目类型与项目成员模型先落地。项目审批与项目认领才有实施基础。本稿设计覆盖项目路径。实施等待前置模型。

## 开放问题

公共库是否可被普通用户选为目标。已定（Owner 2026-10-25）：允许选，选则进入总管理员队列。

拒绝理由是否必填。已定（Owner 2026-10-25）：选填，不强制。

移动审批是目标库单边还是双边。已定（Owner 2026-10-25）：单边，由目标库管理员批；双边未采纳。

总管理员代批权限。已定（Owner 2026-10-25）：允许代批。代批记为代批事件。总管理员可设多个。每个动作审计记操作管理员。

审批队列提醒方式。已定（Owner 2026-10-25）：仅站内待办提醒，不发邮件。
